## 2. 数据从哪里获取

### 2.1 主数据：AliMeeting4MUG

- [ModelScope 国内入口](https://www.modelscope.cn/datasets/modelscope/Alimeeting4MUG)
- [ModelScope 数据说明](https://www.modelscope.ai/datasets/modelscope/Alimeeting4MUG)
- [官方处理代码与说明](https://github.com/alibaba-damo-academy/SpokenNLP/tree/main/alimeeting4mug)

官方数据说明介绍了中文会议语料及行动项检测等任务，样例中包括 `meeting_key`、`sentences` 和 `action_ids`。数据页标注 CC BY 4.0。代码仓库的许可与数据许可应分别记录，不混用。

**我们需要的是会议文字与行动项标签，而不是只有话题分割标签的子集。** 官方加载示例区分 `default` 和 `only_topic_segmentation`，并使用 ModelScope SDK Token。旧示例不保证能直接在当前环境运行，加载参数和依赖应经小样本验证再锁定。

数据卡描述的完整语料规模，不代表当前账号能直接下载同样数量的带标签样本。实际可用的 train/dev/test、每个划分是否有行动项标签，都要读取后确认。

### 2.2 用户手动下载时怎么做

1. 登录 ModelScope，进入上述数据集页面。
2. 查阅数据说明和文件列表，优先找带会议正文及行动项标签的文本数据。
3. 先获取少量原始会议或最小可用文件。不要只复制网页截图、只下载摘要，或提前把标签删除。
4. 原件放到项目根目录下计划使用的 `data/raw/alimeeting4mug/`。此目录将在数据阶段建立。
5. 保留原文件名和压缩包；同时记录下载日期、来源链接、子集和版本。
6. 如果页面只能通过 SDK 加载，使用本机登录或环境变量配置凭证；不用把 Token 写进 Markdown、代码仓库或聊天消息。

遇到登录或访问限制时，记录具体阻塞，不从许可不明的转载包替换数据。

### 2.3 必须保留的字段

| 字段 | 含义 | 用途 |
|---|---|---|
| `meeting_key` | 原始会议标识 | 划分数据、追踪来源、防止泄漏 |
| `sentences[].id` | 句子编号 | 训练目标和证据定位 |
| `sentences[].s` | 会议文字 | 模型输入、检索语料 |
| `sentences[].speaker` | 会议内说话人编号 | 展示与后续人物指代分析 |
| `action_ids` | 行动句标注 | 第一阶段监督目标 |
| 起止时间等可用元数据 | 会议中的位置 | 辅助定位；不等于会议日历日期 |

这些字段名来自公开样例，实际文件可能还有嵌套、JSON 字符串或分隔格式，需要在解析时确认。其他原始字段先保留，不为了第一版用不到而从原件中删除。

**重要区别：** 时间偏移不能用来推导“周五”的具体日期；说话人编号不能跨会议直接合并为同一个人。

## 3. 下载后必须完成的数据审计

产出一份 `data_audit.md` 和来源清单，至少回答：

- 实际有多少场会议？各划分分别多少？哪些有可用行动项标签？
- 标签缺失、显式空列表、解析失败分别有多少？**只有确认标注完整的空列表才是负样本。**
- 会议 ID 是否唯一？句子 ID 是否重复？所有标签能否定位到正文？
- 多人标注在文件里如何呈现？沿用官方合并结果还是需要另定规则？
- 各会议和句子的长度分布、行动句比例是什么？
- 不同划分是否有重复会议、相同转录文本或重复版本？
- 是否包含可直接使用的独立测试标签？没有则从可用标注会议中按会议划分独立测试集，并注明是自建划分。

来源清单建议记录：来源 URL、子集、文件名、下载日期、版本/修订号（如可获取）、SHA-256、许可、解析器版本、实际条数。

原始数据只读保留。清洗后的标准数据另存，不能覆盖原件。

## 4. 训练数据需要怎样准备

第一阶段目标是“上下文中的哪些句子属于行动项”，不是预测用户是否真的完成任务。

建议步骤：

1. 按整场会议确定训练、验证、测试划分，优先保留官方划分。
2. 将会议转成统一的句子列表，保留原会议 ID、句子 ID 和说话人。
3. 采用连续短窗口，按实际 tokenizer 的 token 数控制长度；不能仅按汉字数估计。
4. 用原始标签生成窗口内的行动句编号列表，缺失标签不得转成空列表。
5. 对重叠窗口明确“上下文区”和“待预测中心区”，避免边界句多次计分。
6. 保留有行动项与无行动项的样本。训练时可控制比例，验证/测试保持自然分布并报告比例。
7. 人工抽查正例、负例、长句、跨句承诺、搁置事项及窗口边界。

建议先整理约 1,000～3,000 条有效窗口样本，输入与输出总长度从 1,024～2,048 tokens 起步。样本数和长度是暂定范围，不为凑数重复复制，也不因此截断掉标注句。

数据中常见的讨论或建议是否算行动项，以数据集标注定义为准。产品需要的“是否可以创建任务”是另一层判断，不能擅自重写官方标签后仍报告官方任务成绩。

## 5. 哪些内容需要自己补充

### 5.1 任务字段评估集

行动句标签不等于完整的任务字段标签。需要补一小批人工核对的数据，用来评估：

- 任务描述及原文证据；
- 负责人是明确、指代可解析，还是未知；
- 截止时间原话、是否可归一化为日期；
- 承诺、建议、撤回、暂缓等状态；
- 一句多个任务、多个句子同一任务等情况。

建议先做 30～50 个候选事项，覆盖无行动项和歧义案例。区分来源会议所在划分；测试集补充标注不得回流到训练或提示词示例。

### 5.2 模拟业务数据

自己建立少量演示成员和已有任务，明确标记为模拟数据。会议中的 `no.0` 等编号需由用户映射到成员；无依据时不自动认人。

任务状态由用户或任务工具的真实返回更新。不能用模型猜测“已完成”。

### 5.3 系统测试场景

准备约 20～30 个流程案例：证据不足、缺负责人、无会议日期、用户拒绝、取消后重新编辑、重复点击确认、工具超时、进程重启、数据修改后旧草稿失效等。

## 6. Mac、服务器和模型准备

### Intel Mac

本地负责文本处理、应用开发、数据库、界面和评估结果分析。环境安装前检查实际内存、磁盘、系统版本和依赖兼容性。

建议分离应用环境与训练环境。先用模拟模型返回值把流程跑通，不为调界面持续租 GPU。

Embedding 先选可在 CPU 跑的小型中文/多语言模型，按批次离线构建索引。具体模型在小样本检索验证后确定。

### GPU 服务器

- 起步按单张 24GB 显存 NVIDIA GPU 规划；实际能否运行以短程试验为准。
- 主要用途：QLoRA 微调、批量评估，必要时在演示期间提供推理接口。
- GPU 租用前落实预算上限、数据上传方式、模型下载空间和结果备份。
- 先测 20～50 条样本、少量训练步，再根据峰值显存和实测速率估算正式任务成本。
- 训练后下载 Adapter、配置、日志、预测和评估报告，核验文件，再停止实例计费。

### 模型与账号

| 用途 | 起步方案 | 说明 |
|---|---|---|
| 行动句微调 | `Qwen/Qwen2.5-1.5B-Instruct` | 优先建立低成本基线，官方模型页标注 Apache 2.0 |
| 对话与工具决策 | 已有、经测试支持工具调用的指令模型/API | 负责选工具、追问、整理回答；不把这部分效果算成小模型微调效果 |
| 检索向量 | 小型中文/多语言 Embedding | CPU 建索引；具体型号待检索试验 |
| 追踪 | LangSmith + 本地结构化日志 | 托管追踪需账号；不上传密钥，控制记录内容 |

模型来源：[Qwen2.5-1.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct)。

第一版不必准备多卡服务器、全参数微调环境或长文本训练集。Intel Mac 上的量化 CPU 推理作为可选验证，未测速度前不承诺实时体验。
