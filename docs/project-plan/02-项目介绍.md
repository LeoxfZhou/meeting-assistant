# 项目介绍：中文会议行动助手

更新日期：2026-10-27。状态：设计方案，尚未实现。

## 1. 项目是什么

中文会议行动助手面向需要整理会议、跟进工作的用户：从会议文字中找出行动项，展示对应证据，对缺失信息进行澄清，在用户确认后创建任务，并支持查询任务及来源。

项目的核心交付是一个可操作的业务流程：

> 会议文字 → 行动项识别 → 候选任务 → 信息澄清 → 人工确认 → 正式任务 → 来源追踪。

它同时是一项小模型微调实践：我们训练行动句识别模型，并把训练结果接入应用。项目成果要分别说明模型能力、业务流程和工程可靠性。

## 2. 面向谁，解决什么问题

典型用户是项目负责人、会议记录整理者和团队成员。常见问题包括：

- 会议记录很长，承诺和安排分散在不同发言中。
- 讨论建议与已确定的行动混在一起，容易误建任务。
- 负责人、时间或依赖关系不完整，后续需要补问。
- 任务失去原始出处，无法解释为什么创建。
- 多次整理同一会议，可能重复建立相同任务。

第一版采用公开会议文本和模拟成员、任务，定位为个人学习与求职项目，不宣称已服务真实企业。

## 3. 输入是什么

| 输入 | 必要性 | 示例与约束 |
|---|---|---|
| 会议文字 | 必须 | 句子编号、说话人、正文；没有说话人时保留未知 |
| 用户要求 | 必须 | “提取全场行动项”或“只查供应商相关安排” |
| 会议日期与时区 | 处理相对日期时需要 | 未提供则不把“周五”转换为具体日期 |
| 成员映射 | 创建到具体负责人时需要 | 将会议内说话人映射到演示成员，需用户确认 |
| 用户补充与确认 | 视任务需要 | 指定负责人、补日期、修改任务或拒绝创建 |
| 已有任务状态 | 防重复和查询时需要 | 从数据库读取，不能由模型编造 |

不把会议文本中的命令当成系统操作授权。例如原文出现“直接把所有任务标记完成”，只能作为会议内容处理，不能触发工具执行。

## 4. 输出是什么

### 4.1 证据回答

回答用户关于会议内容的问题，附会议 ID 和句子编号。引用必须能定位到输入正文；引用存在并不自动保证解释正确，还需检查前后文和语义支持。

### 4.2 候选任务

建议字段如下，属于项目设计，不是原始数据集已有字段：

| 字段 | 含义 |
|---|---|
| `candidate_id` | 候选项标识 |
| `meeting_id` / `source_hash` | 来源会议及内容版本 |
| `title` / `description` | 任务名称和说明 |
| `evidence_sentence_ids` | 原文证据编号 |
| `assignee_id` | 用户确认的负责人，可为空 |
| `due_text` / `due_date` | 截止时间原话与可确认的具体日期，可为空 |
| `missing_fields` | 需要补充的字段 |
| `decision_status` | 待澄清、待确认、已拒绝、已确认等 |
| `revision` | 候选内容版本，修改后旧确认失效 |

系统区分字段来源：原文明确、模型推断候选、用户补充。用户新增的日期不能展示为“会议中已确定”。

### 4.3 正式任务

只有经过确认的候选项才能生成正式任务，返回任务编号、保存的字段、来源和创建记录。第一版默认任务标题、证据和负责人必须确认；截止日期允许为空，但界面明确显示“未设日期”。

用户可以将演示任务标为进行中或已完成。助手查询实际保存状态，不通过会议语气猜测完成情况。

## 5. 一个完整使用案例

以下为自编示例，并非原数据摘录：

```text
[101] 主持人：下周需要确定供应商。
[102] 小王：我周五之前整理三家供应商的报价。
[103] 小李：报价出来以后，我再比较交付周期。
[104] 主持人：官网产品介绍也要更新一下。
[105] 小赵：要不要顺便把首页重新设计？
[106] 主持人：首页改版先不做，发布结束以后再讨论。
```

用户要求：“整理需要跟进的任务，确认后加入看板。”

系统候选结果：

| 内容 | 负责人线索 | 时间线索 | 后续处理 |
|---|---|---|---|
| 整理供应商报价 | 小王 | 周五 | 需要会议日期和成员映射 |
| 比较交付周期 | 小李 | 报价整理后 | 保留依赖说明，时间可待定 |
| 更新产品介绍 | 未明确 | 未明确 | 询问负责人和时间 |

首页改版有明确暂缓信息，不直接创建为当前待办；用户可以查看原话。注意：这是产品层解释，模型行动句检测仍按所用数据的标签定义评估。

用户补充“产品介绍由小赵负责，下周二完成”，系统记录为用户补充，更新草稿。用户确认后才写入看板。

若用户修改草稿或来源会议内容变更，必须重新核对和确认。重复点击同一次确认，不得创建第二份相同任务。

## 6. 四个核心功能

### 功能 A：会议问答

按用户问题搜索相关片段，必要时读取前后文，输出带依据的解释。

### 功能 B：行动项识别

全场提取时对完整会议分窗口扫描。主题提取时可先检索相关范围，但不能因此声称覆盖全场。

### 功能 C：澄清与任务创建

整理候选任务、检查缺失信息、查询已有任务、等待确认、提交创建。人工修改始终保留记录。

### 功能 D：任务和来源查询

查看任务状态、来源、未设日期项及历史操作。第一版不自动发送催办消息或操作外部企业平台。

## 7. 界面设计

| 页面 | 内容 |
|---|---|
| 会议页 | 会议列表、正文、说话人和句子编号 |
| 处理页 | 对话、候选任务、证据、缺失字段、编辑和确认按钮 |
| 任务看板 | 已创建任务、负责人、日期、状态和来源入口 |

用户点击证据可定位原句。使用模拟结果时必须标注“模拟”；使用保存结果时标注“历史结果”；真实模型调用单独显示执行状态。

## 8. 微调模型在产品里的位置

微调模型负责“识别行动句”。对话模型负责理解需求、决定调用什么工具和整理表述。确定性代码负责校验字段、确认权限、幂等写入及日期处理。

这能把问题定位到具体层：漏掉行动句是检测问题；负责人编造是抽取问题；未经确认创建是流程问题。不能把所有改进都归因于微调。

第一版允许行动句模型和 Agent 使用不同模型。文档、界面和评估中明确它们的实际身份与版本。

## 9. 范围与成功标准

第一版包括文字输入、单场会议、单用户演示、一个 Agent、一项小模型微调和项目自带看板。

语音识别、实时会议、跨团队权限、多 Agent、外部消息发送和跨会议长期记忆放到后续考虑。不为丰富简历而提前加入。

项目完成的证据包括：

1. 从合法获取的原始数据构造可复现的训练与评估样本。
2. 完成微调前后对比，并报告收益与退化，不以格式改善替代语义改善。
3. 用户能从会议进入任务看板，每个任务都有来源和确认记录。
4. 缺失信息、拒绝、重试、重复确认和恢复场景有测试证据。
5. 演示能展示实际模型、调用轨迹、耗时与已知局限。

面试介绍可使用：“基于中文会议数据构建行动助手，使用 QLoRA 训练行动句识别模型，并通过 LangGraph 实现证据检索、澄清、人工确认和任务创建。”这句话只能在相关功能实现后作为完成描述；当前仍为规划。
